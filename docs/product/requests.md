# Request и пользовательские сценарии

Основание: исходный PRODUCT draft 0.1, разделы 3–4, 10, 12, 22, 25–26, 29, 34, 46–47.


## Одна Request

Requester создает Request для получения результата Service.
Внутри могут работать несколько Team, Task, Approval, веток и автоматических действий.
Для Requester сохраняются один номер, история, Public Status, публичная переписка, результат и оценка.

Request MUST ссылаться ровно на один Service Release.
Правила сохранения этой связи находятся в [Service Release](../architecture/service-release.md).
Вопрос о привязке черновика отмечен как D-04 в [состояниях](statuses.md).

## Действия Requester

Requester может сохранить черновик, отправить Request, посмотреть свои Request и ответить на запрос информации.
Он может написать Public Message и добавить вложение.
Отмена доступна, если ее разрешает политика.
Исходник также предусматривает подтверждение результата и оценку качества.

Страница Request показывает номер, название Service, Public Status и простую историю.
Она показывает разрешенные исходные данные, текущий запрос к Requester, сообщения, результат и доступные действия.
Requester не видит технические Node, служебные Task, Internal Note, ошибки интеграций, системные поля и внутренние SLA.
Закрытые поля не включаются в представление.

[Состояния](statuses.md) задают Public Status и примеры mapping.
[PublicRequestView](../architecture/permissions.md) задает серверную границу представления.

> DECISION REQUIRED — D-06: подтверждение и отмена.
> Исходник разрешает подтверждение результата и отмену по политике, но не описывает переходы и влияние на активные Task.
> Это влияет на окончательность результата, сроки и остановку исполнения.
> В тексте есть успешное завершение через End Success и отдельное действие подтверждения; их порядок не задан.
> До реализации этих действий нужно определить разрешенные состояния, полномочия и последствия.

## Уточнение данных

Request Information переводит Request в «Ожидаем вас».
Requester получает вопрос, дополнительные поля или запрос вложения.
После ответа workflow продолжает исполнение.
Пауза SLA зависит от политики; [коммуникации](../architecture/communications.md) содержат полный критерий приемки.

## CSAT

После успешного завершения Service может запросить оценку 1–5, комментарий и необязательные теги.
Примеры тегов: «быстро», «непонятно», «удобно».
Владелец услуги видит агрегированные результаты.
Оценка MUST NOT напрямую менять SLA конкретного исполнителя без отдельной модели.

## Эталонные Service полного MVP

Это демонстрационные сценарии исходника. Они не расширяют scope M01.

| Service | Поля формы | Маршрут | Что проверяет |
|---|---|---|---|
| Получить доступ в систему | Система; тип доступа; причина; срок доступа | Start → Approval руководителя → Condition «привилегированный доступ?» → для privileged Security Approval → IT Task → End Success | Approval, Condition, assignment, видимость полей, результат |
| Подготовить рабочее место новому сотруднику | Сотрудник; дата выхода; локация; профиль оборудования | Start → Parallel Split: IT (аккаунт/ноутбук), Facilities (место/офис), HR (документы) → Join ALL → End Success | Параллельность, ALL, разные Team, SLA |
| Закупка оборудования | Наименование; обоснование; стоимость; cost center | Start → Approval руководителя → Condition amount: ниже limit — Procurement Task, иначе Finance Approval → Procurement Task → Request Information по условию → End Success | Условное согласование, уточнение, финансовые поля, пауза SLA |
| Проблема с рабочим компьютером | Устройство; описание; срочность; вложение | Start → IT Queue Task → Condition solved: да — End Success, нет — Specialist Task → End Success | Очередь, конкурирующий claim, переназначение/эскалация, публичная коммуникация |

Значение `limit` не задано. Оно относится к настройке конкретной Service.
Сложный onboarding с проверкой данных и контролируемым возвратом описан в [каталоге Node](../architecture/workflow-nodes.md).

## Пример полного пользовательского пути

1. Сотрудник открывает портал и ищет «доступ в BI».
2. Он выбирает Service «Доступ к аналитическим системам».
3. Он читает описание и ожидаемый срок, заполняет четыре поля и отправляет Request.
4. Система показывает номер `REQ-2026-00124` и «Принята».
5. Workflow определяет руководителя и получает Approval.
6. Security участвует только для privileged role.
7. IAM забирает Task из очереди. Requester видит «Выполняется».
8. IAM указывает выданную роль и завершает Task.
9. Requester видит «Завершена», результат «Доступ предоставлен» и действие оценки.

Формат номера в примере не является утвержденным правилом нумерации.
[ROADMAP](../../ROADMAP.md) определяет этапы достижения полного сценария.
