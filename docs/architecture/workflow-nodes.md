# Типы Node и семантика ветвления

Основание: исходный PRODUCT draft 0.1, разделы 9, 24–26, 39, 47.


## Каталог

| Node | Поведение и настройки из исходника | Очередность по текущему плану |
|---|---|---|
| Start | Запускается после создания Request; outputs: request, requester, service, release, context | M01 |
| Human Task | Создает Task исполнителю или очереди; title template, instructions, assignment rule, input fields, output form, due policy, field visibility, allowed actions | Минимум M01; настройки расширяются позже |
| Approval | Создает согласование; один согласующий или список; режимы ANY, ALL, N_OF_M | Последовательное M04; коллективное M05 |
| Condition | Маршрутизирует по expression, например `request.amount > 100000` | M04 |
| Switch | Выбирает именованную ветку | M04 |
| Parallel Split | Запускает несколько веток | M05 |
| Join | Объединяет ветки по ALL, ANY, N_OF_M | M05 |
| Request Information | Запрашивает вопрос, дополнительные поля или вложение; публичное ожидание и пауза SLA по политике | M06; SLA M08 |
| Send Message | Отправляет Public Message или сообщение внутреннего канала | M06 |
| Wait / Timer | Ждет время, дату, SLA-offset или время Business Calendar | M08 |
| Create Record | Создает запись Frappe DocType | Ограниченный Action пилота; набор Q14, завершение M10 |
| Update Record | Изменяет запись Frappe DocType | Ограниченный Action пилота; набор Q14, завершение M10 |
| Integration Action | Выполняет зарегистрированное действие | По Q14; надежность M10 |
| Subflow | Запускает повторно используемый внутренний workflow | D-03; не включен молча в ранние milestone |
| End Success | Завершает Request успешно | M01 |
| End Failure | Завершает Request отказом или невозможностью исполнения | M04 |

Результаты Approval перечислены в [состояниях](../product/statuses.md).
Примеры Integration Action: создать аккаунт, выдать группу доступа, создать внешнюю задачу, отправить документ на подпись.
Примеры Subflow: согласование руководителем, проверка Security, создание закупки.
Они иллюстрируют механизм и не требуют реализации всех действий в M00–M10.

## Join и оставшиеся ветки

| Режим | Условие продолжения |
|---|---|
| ALL | Завершены все требуемые ветки |
| ANY | Первая ветка успешно завершилась |
| N_OF_M | Успешно завершились N из M веток |

Исходник перечисляет три политики оставшихся веток:

- `cancel`: отменить незавершенные ветки;
- `continue in background`: продолжить их в фоне;
- `wait but do not block public result`: ждать, не блокируя публичный результат.

Для первого этапа Parallel исходник рекомендует `cancel` и `continue`.
Этот этап запланирован в M05; Parallel входит в Product Scope и остается Out of Scope for M01.
Система MUST NOT сводить ALL, ANY и N_OF_M к одному правилу.
Join MUST продолжаться ровно один раз при конкурирующем завершении веток.

## Приемка параллельного исполнения

| Сценарий | Ожидаемое поведение |
|---|---|
| ALL, три ветки, завершены две | Join не проходит |
| ALL, затем завершена третья | Join проходит ровно один раз |
| ANY, три ветки, policy cancel remaining, первая успешна | Join проходит, остальные незавершенные ветки отменяются |
| N_OF_M, N=2, M=3, две успешны | Join проходит; третья следует опубликованной policy |

> DECISION REQUIRED — D-12: терминальные ветки и итог.
> Не определено поведение ALL при failure/cancel, достижимость N при отказах и итог Request при фоновых ветках.
> Это влияет на завершение, отмену Task, поздние outputs и однократность Join.
> Исходник задает успешные сценарии и три политики оставшихся веток, но не полную семантику.
> До M05 нужно утвердить матрицу исходов и связь публичного результата с продолжающейся работой.
>
> DECISION REQUIRED — D-13: коллективное Approval.
> Не определены сочетания approved/rejected/returned/cancelled для ANY, ALL и N_OF_M.
> Это влияет на бизнес-решение согласования.
> В тексте есть список режимов и результатов; правила Join не определяют автоматически результат Approval.
> До коллективного Approval нужно утвердить отдельную таблицу решений.

## Контролируемый возврат

Пример сложного onboarding из исходника:

```text
Start → проверка данных сотрудника
      → некорректны: запрос уточнения HR → контролируемый повтор проверки
      → корректны: Parallel Split
          → IT: аккаунты
          → IT: оборудование
          → Facilities: пропуск
          → HR: документы
        → Join ALL → End Success
```

Возврат в этом примере не является разрешением произвольной graph-edge петли.
Рекомендация по циклам находится в [Workflow Definition](workflow-definition.md).

> DECISION REQUIRED — D-03: границы набора Node.
> Раздел «Ноды первой версии» включает Subflow, Create Record и Update Record.
> Историческое расхождение исходника: перечень MVP использует обобщенный Action и не включает Subflow; другой раздел рекомендует Subflow для MVP.
> Repeat Block упомянут для возвратов, но его контракт отсутствует. Пример уточнения HR отличается от запроса Requester.
> Это влияет на scope и модель повторного исполнения.
> До зависимых Slice нужно определить минимальный Action, очередь Subflow/Repeat Block и получателя внутренних уточнений.

## Вторая очередь

Архитектура должна учитывать webhook wait, inbound event, document generation, electronic signature и script/code node.
Также предусмотрены foreach, loop, AI action, child request, compensation/rollback и escalation subflow.
Это будущие возможности, а не разрешение включить их в M01.
[ROADMAP](../../ROADMAP.md) сохраняет их вне раннего scope.
