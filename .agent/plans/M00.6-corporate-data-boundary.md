# M00.6 — Corporate Data Boundary

## Goal

Record a verified mapping of the corporate-data surfaces relevant to Service Hub
and establish the smallest approved Data Provider Layer contract so a later
slice can read an allowed corporate reference without direct dependence on
`itnovel_common` DocTypes. The acceptance result is one server-side,
permission-checked allowed-read example and one denied-read example.

## Current State

### CONFIRMED

- The Bench is Docker-backed Frappe 16.36.1 / Python 3.14.7. The development
  site has `frappe`, `itnovel_common`, and `service_hub_system`; the isolated
  `service-hub-tests.localhost` site has only `frappe` and
  `service_hub_system`.
- Service Hub has no provider package, provider-registration hook, corporate
  adapter, required app, corporate-data DocType, or direct `itnovel_common`
  import. Its only backend test is the M00.4 package-version smoke test.
- `itnovel_common` owns candidate people, employee, department, position,
  organization, and person-document records. Its `resolve_employee_for_user`
  resolves a Frappe user to one employee and returns no result for Guest or an
  ambiguous match. This is an implementation candidate, not a published
  Service Hub contract.
- The inspected Supervisor endpoints check Common's DocType permissions, but
  their projections are broader than the prospective Service Hub boundary:
  `get_person` returns owner and person details; employee endpoints can return
  contact, identity, employment-history, and conditionally sensitive fields.
  `ITN Person` fields and Employee fields include sensitive identifiers and
  contacts under Common's own permission model.
- No `ITN Team` source, ManagerResolver, Service-Hub-specific
  PermissionResolver, or explicit mapping from Service Hub roles/policies to
  Common permissions was found. No selected multi-company or SSO policy was
  found.
- D-21 is now accepted for M01 in
  [the existing-app boundary](../../docs/architecture/existing-app-boundary.md):
  a corporate adapter resolves only an active employee identity; Service Hub
  owns routing Team and membership; effective access is corporate grant AND
  Service Hub contextual policy. Manager, organization, document, and broader
  employment contracts remain deferred.

### INFERRED

- Existing Common endpoints and its internal DocTypes cannot be treated as the
  provider API: doing so would couple Service Hub directly to implementation
  detail and would return more data than its future safe projections need.
- A Service Hub contract test can run on the isolated test site only with a
  fake provider. A real Common-adapter integration test needs an approved,
  non-production fixture boundary; it must not use `development.localhost`
  data.

### MISSING

- No real `itnovel_common` adapter factory or approved non-production Common
  fixture exists. It is intentionally outside this Slice: the accepted
  implementation evidence is an isolated fake provider.

## Scope

- M00.6 only: the accepted M01 corporate-identity contract and its smallest
  executable Service Hub seam.
- Implement the versioned registration lookup, narrow identity projection,
  fail-closed denied results, and a pure effective-access conjunction used by
  the future Team queue. Prove it with an isolated fake provider on
  `service-hub-tests.localhost`.

## Non-Goals

- No Service, Request, Task, workflow, Team queue, Dynamic Form, Action,
  Service Release, migration, or corporate master-data copy.
- No direct read of `ITN Person`, `ITN Employee`, `ITN Department`, or other
  `itnovel_common` DocType from Service Hub.
- No change to `itnovel_common`, no real corporate-data test against
  `development.localhost`, no production adapter, SSO, manager fallback,
  multi-company policy, or field-level ACL design.

## Decisions Required

**Resolved — D-21 for M01 only.** The provider contract id is
`corporate-identity/v1`; the mandatory Frappe registration key is
`service_hub_corporate_identity_provider`; `CorporateRef` is an opaque
`corpref:v1:employee:<opaque-id>` reference; the sole permitted identity
projection contains `corporate_ref` and `display_name`; and all missing,
ambiguous, inactive, incompatible, or failed provider paths deny without
corporate data. Service Hub owns routing Team and membership. Manager,
organization, document, advanced employment, bulk-read, and cache semantics
remain deferred as documented and are not implemented here.

## Implementation Plan

1. Preserve the accepted D-21 decision in
   `docs/architecture/existing-app-boundary.md`; do not turn Common candidates
   into direct Service Hub dependencies.
2. Add only the approved Service Hub registration seam and narrow typed result
   for the selected first read. The provider receives actor/context explicitly
   and returns a deny/not-found result without fallback to direct DocType
   access.
3. Add a fake provider to an isolated Service Hub test. The allowed case
   returns exactly the approved minimum projection; the denied case proves an
   unauthorized actor receives no corporate value. The test must run on
   `service-hub-tests.localhost` and contain no Common fixture or development
   data.
4. Prove the approved Team-access conjunction without creating a Team or Task:
   a corporate grant without membership and a member with corporate deny both
   fail closed. A real Team queue remains M01.

## Risks

- A real adapter registered in `itnovel_common` is not part of M00.6. Until it
  is supplied by its owner, runtime resolution denies safely.
- Reusing development-site data would pollute or disclose corporate data.
- Treating Common ACL as the full Service Hub authorization decision would
  violate the server-side safe-projection invariant.

## Rollback

Revert the Service Hub provider package and its fake contract test. Do not
alter corporate records, test-site databases, or existing Common interfaces
automatically.

## Acceptance Criteria

1. The provider mapping names an approved source and contract rather than an
   inferred Common DocType or endpoint.
2. The contract defines one server-side permitted read and one denied read,
   including the minimum returned data and deny behavior.
3. The automated test runs only on the isolated Service Hub test site.
4. No direct product dependency on an internal `itnovel_common` DocType or
   undocumented endpoint is introduced.
