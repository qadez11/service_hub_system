## Goal

On every pull request and push to `main`, GitHub Actions can provision an isolated Frappe test environment and run the existing backend smoke plus frontend and Python quality checks, failing the workflow when any selected check fails.

## Current State

### CONFIRMED

- `origin` is `https://github.com/qadez11/service_hub_system.git`; no `.github/workflows/` or other app-owned CI configuration exists.
- The frontend lockfile and scripts support `npm ci`, `npm run test`, `npm run type-check`, and `npm run build`. M00.4 recorded successful execution in the Frappe container.
- `pyproject.toml` configures Ruff; `.pre-commit-config.yaml` pins its Ruff hook at `v0.14.10`.
- The backend smoke test runs through Frappe Bench. Frappe's own v16 app CI pattern creates an equivalent ephemeral Bench, MariaDB, Redis services, and site per workflow run, so hosted CI need not access the local Docker test site.
- The worktree is clean before this Slice.

### INFERRED

- GitHub Actions is the smallest CI provider that matches the confirmed GitHub remote and requires no new service account, provider integration, or repository-local runner.

### MISSING / UNKNOWN

- A hosted workflow run cannot be observed until the workflow is pushed to the GitHub remote. Pushing, enabling repository Actions, and configuring any organization policy are outside this Slice unless explicitly authorized.

## Scope

1. Add one GitHub Actions workflow for `pull_request`, pushes to `main`, and manual dispatch.
2. Run the repository-contained frontend checks under the current Node 24 baseline: deterministic install, Vitest, TypeScript check, and Vite production build.
3. Provision an ephemeral Frappe 16 Bench, MariaDB 11.8, Redis cache/queue, and new site within the hosted backend job; install the checked-out app and run the existing backend smoke test.
4. Run Ruff lint and formatting checks for the Python package with the version aligned to the existing pre-commit configuration.
5. Record the selected CI environment and safe developer commands in the milestone document and README.
6. Validate YAML locally, rerun the selected local checks in the existing Frappe container, and use an ephemeral intentionally failing frontend test to prove the test command returns failure.

## Dependencies

- The existing frontend lockfile and current Ruff configuration.

## Decisions Required

- **Resolved for M00.5:** select GitHub Actions hosted Ubuntu runners because the app's only configured remote is GitHub. The selected baseline uses an ephemeral Frappe 16 Bench/MariaDB/Redis/site for the existing backend smoke, plus Node 24 frontend checks and Ruff static checks. It does not connect to any local or production environment.
- D-21 and all Request/Service Release/workflow decisions do not apply: no product or corporate data is read or changed.
- If hosted Actions are disabled or organization policy requires another provider, stop before changing to an unverified platform; that is a new explicit infrastructure decision.

## Implementation Plan

1. Add `.github/workflows/ci.yml` with separate `backend-smoke`, `frontend`, and `python-quality` jobs.
2. The frontend job checks out source, installs Node 24, runs `npm ci` in `frontend/`, then runs test, type-check, and build without a dev server or backend request.
3. The backend job uses Frappe v16's CI-compatible Python 3.14, Node 24, MariaDB 11.8, and two Redis services. It initializes a disposable Bench from Frappe `version-16`, installs this checkout and its requirements, creates a fresh `test_site`, and runs the current app smoke suite.
4. The Python-quality job checks out source, installs Python 3.14, installs `ruff==0.14.10`, then runs `ruff check service_hub_system` and `ruff format --check service_hub_system`.
5. Update the main M00 document's CI decision from open to the selected baseline and state its ephemeral test environment. Update README with CI scope and local equivalent commands.
5. Run the checked commands in the existing Frappe container. Parse the workflow YAML locally and create/remove one temporary failing Vitest spec, expecting a non-zero result; then confirm the regular suite passes and the tree contains no probe.

## Risks

- Hosted verification is unavailable until a permitted push; local success validates workflow inputs and commands, not GitHub's execution environment.
- Registry/network unavailability on a runner can fail deterministic installs. This is surfaced as a pipeline failure, not hidden by cache or a fallback.
- A need for a fully provisioned Bench/MariaDB/Redis test environment in this repository is scope expansion and requires a separate plan.

## Rollback

Revert the workflow and accompanying documentation changes. This Slice creates no database records, migrations, generated tracked assets, jobs, or external side effects. The temporary failure probe is removed before completion.

## Acceptance Criteria

1. A valid GitHub Actions workflow exists for pull requests, pushes to `main`, and manual dispatch.
2. The workflow contains the isolated backend smoke, four selected frontend checks, and two selected Ruff checks.
3. The selected normal checks pass in the intended Frappe container.
4. An isolated intentionally failing frontend probe produces a non-zero test command and leaves no tracked/untracked probe behind.
5. The workflow and docs contain no secrets and do not use `development.localhost` or the local test site as a hosted CI fixture.
6. The hosted ephemeral Bench boundary is documented; no local or production site is used by CI.
7. `git diff --check` passes.
