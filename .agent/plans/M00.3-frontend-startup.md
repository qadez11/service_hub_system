# M00.3 — Frontend Startup + frontend-to-backend smoke

## Current State

- `frontend/` is an npm project with a lockfile. Its installed dependency tree currently resolves Vue `3.5.43`, Frappe UI `1.0.0`, Vite `7.3.6`, Vue Router `4.6.4`, TypeScript `5.9.3`, and `vue-tsc` `3.3.12`.
- `frontend/package.json` exposes `dev` (`vite`), `build` (`vite build`), and `type-check` (`vue-tsc --noEmit`), and requires Node `>=20.19.0`. The current host reports Node `22.16.0`; M00.1 records Node `24.20.0` in the Frappe container. No Node upgrade is planned.
- `frontend/vite.config.ts` uses the existing Frappe UI Vite plugin with `frontendRoute: '/service-hub'`. The plugin starts Vite on `8080` for Frappe web port `8000` and proxies `/api` requests to the Bench web process while preserving the requesting site hostname.
- `frontend/src/router.ts` uses browser history rooted at `/service-hub`. The existing `Home.vue` is the only non-business page and already displays the result/error state of the standard `frappe.auth.get_logged_user` call through Frappe UI `useCall`; it is a suitable connectivity probe. It does not read or create Service Hub product data.
- M00.2 installed `service_hub_system` on `development.localhost` and verified that a temporary `bench serve --port 8000` answers `GET /api/method/frappe.ping` as `{"message":"pong"}` when routed with `Host: development.localhost`.
- Existing uncommitted `README.md` and M00.1/M00.2 plan artifacts belong to preceding slices and must be preserved. No source file is planned to change unless a runtime failure proves a minimal correction is necessary.

## Goal

Give a developer a repeatable local command sequence that starts the existing Vue/Frappe UI application, opens `/service-hub`, and demonstrates an HTTP request from that application path through the Vite proxy to the `development.localhost` Frappe backend with a successful standard-framework response.

## Non-Goals

- No Service, Request, Workflow, Task, Approval, Knowledge Base, business DocType, or product API.
- No provider layer, `itnovel_common` change, Docker refactor, CI, e2e framework, dependency upgrade, or Node upgrade.
- No new state-management library, frontend architecture refactor, authentication model change, or production deployment.
- No backend code or endpoint. The existing Frappe `frappe.ping` endpoint and Home connectivity call are sufficient.

## Frontend Runtime

1. Confirm package installation with `npm --prefix frontend ls --depth=0` and run `npm --prefix frontend run type-check`.
2. Start the existing Bench web command in the Frappe container: `bench serve --port 8000`.
3. Start the existing Vite command in the same container from `apps/service_hub_system/frontend`: `npm run dev`.
4. Verify that Vite reports `development.localhost` at port `8080`, and request `http://127.0.0.1:8080/service-hub/` with `Host: development.localhost:8080` from inside that container. The response must be the Vue entry page without a server error.
5. Build using `npm --prefix frontend run build` only after the dev path works. The existing Frappe UI plugin is expected to write generated assets under the app `public/frontend` directory and the route entry under `www/`; inspect generated output without hand-editing it.

## Backend Connectivity

1. With both processes active, request `http://localhost:8080/api/v2/method/frappe.ping` with `Host: development.localhost:8080` from inside the Frappe container.
2. The Vite proxy must forward the request to the Bench web process using `development.localhost`, and the response must be HTTP 200 with `{"message":"pong"}`. This proves the frontend development origin, proxy, correct Frappe site, backend, and response path.
3. Observe the existing `/service-hub` page response and Vite/Bench logs for runtime or proxy errors. A browser-visible check will be made if an available local browser surface can reach the forwarded port; otherwise the HTTP document plus proxied API observation are recorded as the verifiable limit of this environment.

## Commands

From the app checkout:

```bash
npm --prefix frontend ls --depth=0
npm --prefix frontend run type-check
npm --prefix frontend run build
git diff --check
```

Inside `service_hub_frappe_docker_devcontainer-frappe-1`, with Bench root `/workspace/development/frappe-bench`:

```bash
bench serve --port 8000
cd apps/service_hub_system/frontend && npm run dev
curl -i -H 'Host: development.localhost:8080' http://localhost:8080/service-hub/
curl -i -H 'Host: development.localhost:8080' http://localhost:8080/api/v2/method/frappe.ping
```

Expected observations: dependency tree resolves, type-check and production build exit zero, the route returns the Vue HTML page, and the proxied API response is HTTP 200 with `{"data":"pong"}`. The legacy `/api/method/frappe.ping` response is `{"message":"pong"}`; the v2 variant is used by the existing Frappe UI `useCall` helper.

## Risks

- The Vite proxy resolves its backend using the incoming host name; omitting the `development.localhost` Host header can route to the wrong Bench site and produce a misleading 404.
- A host-run Vite process may not reach container-local port `8000` if Docker does not publish that port. Running Vite in the existing Frappe container is the minimal configuration-consistent alternative, not a Docker change.
- A failure requiring a dependency mass upgrade, Docker rewrite, backend contract change, or `itnovel_common` change is a STOP condition.

## Rollback

Stop the temporary Bench and Vite processes cleanly. Source/document changes are ordinary Git-revertible edits; the build only regenerates the configured frontend assets and route file. This Slice creates no product records, migrations, jobs, or external side effects.

## Acceptance Criteria

1. `npm --prefix frontend run type-check` passes with the installed dependency set.
2. The existing Vite development server starts on its configured port and serves `/service-hub/`.
3. A request through that Vite server reaches `development.localhost` and returns the standard Frappe ping response.
4. `npm --prefix frontend run build` exits successfully and its generated output is inspected.
5. No runtime/browser-visible error is observed in the available environment.
6. No product model, provider layer, backend product code, or `itnovel_common` file changes.
7. `git diff --check` passes and startup commands are documented.

## Open Questions

No product decision blocks this Slice. The future provider contract D-21 is not consulted. Browser-visible verification depends only on whether the local environment exposes a browser surface to the container’s forwarded dev port; it does not authorize an alternate runtime architecture.

- The current host reports Node `22.16.0`, satisfying the manifest minimum. The Frappe container reports Node `24.20.0` and npm `11.19.0`; it is the intended runtime because Bench and backend port `8000` run there.

- `npm run build` passed in the Frappe container. It generated the ignored frontend assets and `www/service-hub.html`; the existing Bench web process served `GET /service-hub` as HTTP 200, and its generated JavaScript entry asset as HTTP 200 `text/javascript`.

No reinstall, dependency update, or lockfile change was made: the build is verified in the actual container runtime. This is an environment limitation for host-only builds, not a frontend source failure.
- Docker exposes no Vite port to the host in the observed environment, so a graphical browser could not reach the container-local dev server without a Docker/forwarding change outside this Slice. The HTTP page, production route, asset, and proxied API smoke checks are the verified limit. Temporary Vite was stopped after verification; the pre-existing Bench web process was left untouched.
