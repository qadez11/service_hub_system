# ExecPlan для одного Slice

ExecPlan описывает одну небольшую вертикальную задачу.
Он связывает Product Scope → Roadmap → Milestone → Slice → ExecPlan → Implementation.
ARCHITECTURE задает технические инварианты.
Он не заменяет продуктовые требования и ADR.

## Когда составлять

Создай ExecPlan перед Slice с несколькими компонентами, изменением модели данных, permissions или concurrency.
Для простой документационной правки достаточно явных границ и проверки ссылок.
Один ExecPlan не должен охватывать весь milestone с Budget XL.
Место хранения конкретного плана согласуй с существующими правилами репозитория; новый каталог этим документом не вводится.

## Правила конкретности

- Прочитай [AGENTS](../AGENTS.md), milestone и связанные источники истины.
- Укажи исходное состояние кода после чтения файлов, а не по памяти.
- Назови точные файлы, методы, contracts и наблюдаемый результат.
- Отдели существующее поведение от планируемого.
- Отметь отсутствующие данные как DECISION REQUIRED.
- Не выдавай PROPOSED модель за принятое решение.
- Для неприменимого раздела напиши «Не применяется» и причину.
- Если Budget XL, раздели работу до реализации.
- Зафиксируй команды проверки, среду и ожидаемые результаты до изменения кода.
- После выполнения запиши фактические результаты, ограничения и отклонения от плана.

## Шаблон

### Context

Укажи milestone, Slice, ссылки на PRODUCT, архитектуру и ADR.
Объясни текущую проблему и почему задача нужна сейчас.

### Goal

Опиши один наблюдаемый результат. Назови пользователя или системного участника.

### Non-Goals

Перечисли исключенные возможности и соседние Slice.

### Existing Code

Укажи прочитанные файлы и текущие точки входа.
Назови используемые providers, tests и ограничения незакоммиченных изменений.

### Files Expected to Change

Для каждого файла укажи роль изменения.
Отдельно укажи документы, которые нужно обновить.

### Data Model Changes

Опиши поля, связи, ограничения и совместимость только в рамках утвержденной модели.
Укажи связь с Service Release и последствия для старых Request.

### Backend Changes

Опиши API, validation, domain logic и job boundaries.
Назови вход, выход и ошибки каждого изменяемого контракта.

### Frontend Changes

Опиши экран, действие и состояния UI.
Укажи серверную projection и отображение отказа доступа.

### Permission Impact

Назови actor, объект, поля, действия и каналы раскрытия.
Укажи серверную проверку и негативные acceptance scenarios.

### Transaction / Concurrency Impact

Назови атомарную операцию, возможную гонку и итог проигравшего запроса.
Опиши identity эффекта, повтор доставки и границу внешнего side effect.

### Migration Impact

Опиши влияние на существующие данные и порядок совместимого развертывания.
После создания Request значение `Request.service_release` MUST NOT изменяться.
[Контракт Service Release](../docs/architecture/service-release.md) действует и для автоматических, и для ручных операций.

### Tests

Перечисли unit/integration/concurrency/E2E проверки, которые доказывают результат Slice.
Укажи команды, среду, fixtures и ожидаемые наблюдения.
Тест не должен только повторять implementation.

### Acceptance Scenario

Опиши исходные данные, actor, последовательность действий и проверяемый результат.
Добавь негативный или конкурентный сценарий, если он существенен для Slice.

### Risks

Назови реальные неопределенности, признаки нарушения инвариантов и условия STOP.

### Rollback

Опиши отмену изменений, влияние на данные и уже запущенные Workflow Execution.
Не обещай откат внешнего side effect без поддерживаемого механизма.

### Open Questions

Перечисли DECISION REQUIRED со ссылками на основной документ.
Для каждого вопроса укажи, какую часть реализации он блокирует.
Зависимая реализация начинается только после явного решения.

## Готовность плана

Другой агент может выполнить Slice без нового проектирования продуктовой семантики.
Файлы и acceptance scenario конкретны. Все блокирующие вопросы закрыты.
План сохраняет [STOP rule](../AGENTS.md).
